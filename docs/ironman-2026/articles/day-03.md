# Day 03｜引用在句尾，證據仍可能不成立

「尚未接受任何來源，匯出內容不會包含可驗證引用。」這是 ResearchForge 早期引用功能裡的一則提醒。然而，沿著當時的下載程式往下看，顯示提醒之後，下一步仍然是匯出檔案。系統已經知道來源有缺口，卻還沒有因此關上出口。[2][3]

上一篇談的是模板與匯出：文件能被交出去，不代表研究已經完成。這篇把問題再往前推一步。即使找到來源、排好參考資料，我還是需要問：那個引用到底支不支持這句話？要回答它，得先知道系統實際保存了什麼，又檢查到了哪裡。

## 引用存在，和引用成立，是兩個問題

我在意的錯誤，不一定藏在明顯荒謬的句子裡。它可能文法正確、前後連貫，句尾也有正式的引用。可是，文末列出一篇文章，只能讓人找到出處；句尾放上標記，也不能替代對來源內容的核對。

可以用一個假設例子理解：來源只記錄「某款工具在特定任務中的表現」，報告卻寫成「這款工具適合所有工作」。即使引用確實指向那份資料，句子的範圍仍然超出了材料。這不是當時某次報告的實測錯誤，而是我用來區分「有引用」與「有支持」的例子。

ResearchForge 在這個階段先處理比較基礎的一端。2026 年 6 月 12 日的引用基礎版本加入來源搜尋、共同資料格式與審查狀態，讓來源不再只是最後附上的一行文字。[1] 這還不是逐句查核，但至少讓「目前用的是哪筆資料」有了可以追查的位置。

## 先讓來源變成能被處理的紀錄

當時的搜尋程式接上 Crossref 與 Semantic Scholar，接收結果後，把不同形狀的資料整理成 `SourceRecord`，也就是一筆來源紀錄。它包含標題、作者、年份、摘要、DOI、網址、來源服務與審查狀態；前後端使用共同的欄位約定。[1]

DOI 在這裡用來識別文獻。至於標題、作者與年份這些描述來源的資料，常統稱為 metadata，中文可稱「中繼資料」。它們幫助我辨認與呈現來源，卻不是來源裡每個研究結論的替身。知道一篇文章叫什麼，和讀懂它究竟支持什麼，是不同工作。

共同格式的好處很具體：審查畫面可以用同一套欄位呈現來源，不必依資料來自哪個服務，就另寫一套作者或年份的處理方式。當時的介面也能編輯標題、作者、年份等資料，並接受或拒絕來源。[1][3] 這讓整理工作有了明確對象，不必直接修改整篇報告。

缺失也需要留下來。歷史程式會把未取得的年份、摘要或 DOI 保留為 `null`，表示沒有可填入的值；沒有作者時則保留空清單。整理過程會清除多餘空白，但不會因為資料列需要完整，就自行補出作者或年份。[1] 共同格式要做到的，是讓缺口看得見，不是讓每個欄位看起來都填好了。

## 接受，是被選用的狀態

搜尋回來的來源預設為 `pending`，表示待審查；使用者可以把它改成 `accepted`（接受）或 `rejected`（拒絕）。當時的前端會先挑出已接受來源，再放進報告生成的輸入；參考文獻的組裝也會篩選接受狀態。[1][2][3]

下面是當時共同來源模組的原始程式節錄。`filter` 會保留符合條件的資料，這裡的條件就是來源的審查狀態：[1]

```ts
export function acceptedSourceRecords(sources: SourceRecord[]): SourceRecord[] {
  return sources.filter((source) => source.reviewState === "accepted");
}

export function rejectedSourceRecords(sources: SourceRecord[]): SourceRecord[] {
  return sources.filter((source) => source.reviewState === "rejected");
}
```

第一個函式只留下已接受來源，第二個則挑出被拒絕的來源，待審查的資料不會通過其中任何一個。不過，這裡只讀取狀態欄位：沒有查看摘要，更沒有拿報告句子與原文比較。`accepted` 代表工作流程中的選用決定，不是每一句相關主張都已獲得證明。

這個差別會影響畫面該怎麼說明結果。「已接受來源」可以描述操作狀態；若改寫成「內容已驗證」，就多承諾了程式沒有檢查的事情。現在回頭看，我會先問狀態是由什麼動作產生，再決定能不能拿它當品質標籤。

## 提醒缺口，不代表阻擋出口

早期程式並沒有把「已接受」與「資料完整」綁在一起。即使來源被接受，作者、年份或 DOI／網址仍可能缺漏。參考資料格式化時，程式會標出缺少的欄位；相關測試也用刻意缺少作者與年份的測試資料，確認輸出保留未提供的提示，而不是補造內容。[2]

這些測試檢查的是資料處理規則，不是一次真實論文審查。它們可以幫我確認缺失有被保留、拒絕的來源不會出現在參考資料裡，卻不能據此宣稱搜尋服務每次都能找到正確研究，更不能說參考資料已經支持整篇報告。[1][2]

匯出提醒則會檢查是否沒有已接受來源、來源資料是否不完整，以及報告裡是否還留著待補引用的文字。以 Markdown 這種用簡單符號標示排版的文字格式為例，下載程式會先呼叫提醒函式，接著直接呼叫下載函式；生成按鈕也沒有以來源不足作為停用條件。[2][3] 開場那個矛盾，正來自這種「告知缺口，但仍可繼續」的設計。

當時完成的是來源選用與缺失提示，尚未把這些提示都變成必須停止的條件。提醒讓人知道有工作未完成；阻擋則決定未完成時能不能繼續。設計研究工具時，兩者必須分別確認，否則一則誠實的警告，也可能被誤認為系統已經處理了風險。

## 這一階段只先解來源身分

還有一個容易被名稱掩蓋的邊界：當時的報告生成器仍是依規則組裝內容的模擬實作，不是已經讓語言模型讀完文獻並逐句驗證。[3] 所以這篇能確認的進展，是來源紀錄進入了審查與報告資料流，不能延伸成自動研究能力已經完成。

現在回頭看，先建立共同紀錄仍然值得。若一筆不該使用的來源出現在參考資料裡，我至少可以沿著它的紀錄查看審查狀態、確認篩選條件，再追到參考資料的組裝。至於來源本身是否支持句子，則需要另外核對，不能期待同一個狀態欄位回答所有問題。

如果你正在做自己的 AI 報告工具，可以挑一筆來源，沿著它走完整條流程：搜尋之後保存了哪些欄位？誰把它從待審查改成接受？哪些輸出真的有讀取這個狀態？最後再挑一句報告文字，回到材料中確認支持範圍。找不到對應內容時，就把那個缺口留下，不要用引用格式替它背書。

這是我從早期實作整理出的追查方法，不是它當時已有的完整防護。每個暫時答不出來的問題，都可以成為下一次改進的具體起點，不必先把整份報告當成一個難以拆解的黑箱。

來源能被辨認與整理之後，下一個問題也更清楚了：進入審查清單的資料，究竟是怎麼被找到的？下一篇會沿著查詢往前追，看看搜尋為什麼開始需要一條可診斷的流程，而不只是一個輸入框。
