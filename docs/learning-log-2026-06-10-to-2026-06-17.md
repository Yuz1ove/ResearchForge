# 2026/06/10｜專案啟動：從「報告生成器」開始建立研究方向

## 當日目標

這一天的主要目標，是先弄清楚「報告生成器網站」到底需要哪些資料、哪些功能、哪些技術架構，以及最小可行產品應該做到什麼程度。最初我並不是直接開始寫程式，而是先把問題拆開，避免一開始就盲目開發。

我當時的核心問題包括：

1. 一個報告生成器網站需要哪些資料？
2. 只靠 AI 輸入框是否足夠？
3. 如果要輸出 PDF 或 DOCX，需要哪些模組？
4. 對學生作品而言，MVP 應該多簡單才合理？
5. 如果未來要擴充成產品，需要預留哪些架構？

## 實作與研究內容

我先整理出報告生成器不只是「AI 幫忙寫文章」，而是需要一整條資料流程。這條流程包含使用者輸入、資料來源、資料清理、模板、生成邏輯、輸出格式與權限管理。

當日整理出的基礎模組包括：

- 使用者輸入主題與需求
- 報告模板設定
- 資料來源設定
- 報告生成紀錄
- 輸出檔案管理
- AI 提示詞與生成規則
- PDF／DOCX 輸出流程

我也初步判斷，如果是學生作品，應該先做半自動 MVP，而不是一開始就做完整 SaaS。最初的 MVP 流程被定義為：

```text
使用者輸入研究主題
→ 選擇報告類型
→ 系統生成報告架構
→ 整理或引用資料
→ 輸出 DOCX／PDF
```

這一天的重要收穫是：我發現報告生成器的核心不是輸入框，而是資料流。若資料流不穩定，AI 產出的報告就容易只是表面完整，實際上沒有研究依據。

## 修改重點

原本我以為網站重點是「讓 AI 寫報告」，但這一天後，我開始把重點改成「建立可追蹤的報告生成流程」。

修改前：

```text
輸入題目 → AI 直接生成報告
```

修改後：

```text
輸入題目 → 搜尋資料 → 整理來源 → 生成架構 → 生成報告 → 輸出文件
```

這個差異很重要，因為它決定了 ResearchForge 後來不是單純的聊天機器人包裝，而是一個研究流程工具。

## 遇到的困難

最大的困難是範圍非常大。報告生成器可以包含很多功能，例如帳號、模板、PDF、DOCX、資料庫、權限、排程、雲端儲存與 AI 生成。如果全部都想做，會變成一個太大的商業產品，而不是高中階段可以完成的作品。

另外，我也發現自己一開始對「報告」這個詞的定義太廣。讀書心得、簡報大綱、商業報告、研究報告、科展報告都可以算報告，但它們的資料需求和寫作邏輯完全不同。

## 解決方式

我先把專案縮小成「研究報告生成器」。因為研究報告最需要來源、文獻、證據與引用，也最能展現系統和一般 AI 工具的差異。

我當時做出的暫定決策是：

1. 不先做完整帳號系統。
2. 不先做商業 SaaS 架構。
3. 不先做太多報告類型。
4. 先支援研究報告與 DOCX／PDF 輸出。
5. 先確認資料流是否能跑通。

## 是否想過放棄

這一天還沒有真正想放棄，但已經感覺到專案比想像中大很多。原本以為只是做一個 AI 網站，研究後才發現這其實涉及前端、後端、資料處理、文件輸出與 AI 流程設計。

## 當日反思

我學到，開始做一個專案時，不能只憑直覺寫功能。尤其是 AI 產品，如果沒有先定義資料從哪裡來、如何被整理、如何被驗證，那麼最後產生的內容可能只是漂亮但不可靠的文字。

## 次日規劃

下一步要開始進入實作，先建立網站基本骨架，測試使用者輸入主題後，系統是否能產出基本報告內容，並觀察實際使用時會出現哪些問題。

# 2026/06/11｜建立網站雛形：發現「萬用報告生成器」容易失焦

## 當日目標

這一天的目標是把前一天的研究轉換成可以操作的網站雛形。重點不是一次做出完整產品，而是先讓頁面能跑起來，並觀察使用者輸入、報告生成與輸出流程是否合理。

## 實作內容

我開始處理網站的基本介面與功能流程，包括：

- 使用者輸入主題
- 選擇報告類型
- 產生初步報告內容
- 檢查頁面顯示是否清楚
- 測試不同主題是否能被正確理解
- 初步思考 GitHub 與部署流程

這一階段也開始出現一些 UI 與產品定位問題。例如頁面上的選項太多，報告類型太雜，甚至有些功能看起來比較像通用 AI 寫作工具，而不是我真正想做的研究資料整理工具。

## 修改重點

我開始刪減或弱化一些不必要的選項。原本頁面可能想支援很多使用情境，例如學校報告、職場報告、簡報大綱、讀書心得、專案文件等。但實際測試後，我發現這會讓使用者不知道系統到底是什麼，也會讓 AI 更容易誤判任務。

因此，我開始將網站方向收斂到：

```text
研究報告
資料搜尋
來源整理
文獻摘要
引用輔助
```

而不是：

```text
任何文章都能生成
任何格式都能輸出
任何使用者都能使用
```

這是一個重要的產品定位修正。

## 遇到的困難

第一個困難是主題理解不穩定。有些主題輸入後，系統會把它理解成軟體專案或開發需求，而不是研究報告主題。例如當題目涉及「網站」、「AI」、「資料」時，系統容易往專案開發方向解讀，而不是學術研究方向。

第二個困難是頁面功能開始變得雜亂。當報告類型、輸入欄位、輸出選項和生成內容都放在同一頁時，整體看起來不夠聚焦。

第三個困難是我開始意識到，如果只是生成一篇文章，這個網站和 ChatGPT 差異不大。這讓我對專案價值產生疑問。

## 解決方式

我把問題分成兩層處理。

第一層是產品定位：

- 不再追求所有類型報告。
- 先專注研究報告。
- 強調資料來源與引用。
- 把「搜尋與整理」放在「生成」之前。

第二層是功能順序：

- 先讓基本輸入與輸出能跑。
- 再處理來源搜尋。
- 再處理證據卡。
- 最後才做 UI 美化與帳號系統。

## 是否想過放棄

這一天開始出現第一次比較明顯的動搖。原因是我發現，如果最後只是做出一個包裝過的 ChatGPT，那它沒有太大價值，也很難作為學習歷程中有特色的作品。

不過，我沒有放棄，而是把這個問題當成重新定位的機會。我開始思考：一般 AI 工具能寫報告，但不一定能幫學生整理來源、判斷資料、建立證據鏈。這正好可以成為 ResearchForge 的核心差異。

## 當日反思

這一天讓我學到，產品開發不是功能越多越好。功能太多反而會讓定位模糊。尤其對學生作品來說，教授或審查者更想看到的是我能不能清楚定義問題、拆解問題並持續修正，而不是一開始就堆滿功能。

## 次日規劃

接下來要更深入思考資料搜尋與主題理解。因為如果系統不能判斷使用者到底要研究什麼，就無法找到正確來源，也無法生成可靠報告。

# 2026/06/12｜拆解核心資料流：從 AI 生成轉向資料搜尋與引用

## 當日目標

這一天的主要目標，是重新拆解 ResearchForge 的核心資料流。我開始意識到，AI 的文字生成能力不是最困難的部分，困難的是如何讓 AI 有正確、可靠、可引用的資料作為依據。

因此，當日重點放在：

1. 主題理解如何改善。
2. 搜尋結果如何更相關。
3. 來源資料如何進入報告生成流程。
4. 本地模型與雲端模型在專案中各自扮演什麼角色。
5. 如何避免 AI 產生看似合理但沒有根據的內容。

## 實作與討論內容

我開始把研究報告生成拆成更明確的階段：

```text
主題輸入
→ 主題分類
→ 關鍵詞生成
→ 搜尋來源
→ 來源篩選
→ 摘要整理
→ 證據提取
→ 報告架構
→ 正文生成
→ 引用與輸出
```

這個流程比原本的一次生成更繁瑣，但也更接近真實研究過程。

我也開始思考本地 AI 是否能提高效果。當時的想法是，前半段資料搜尋與整理其實已經像是建立一個「另類 AI」，如果後半段再接入本地模型，可能能在成本、速度或隱私上有優勢。

但經過思考後，我認為當前最重要的不是先接更強模型，而是先把資料流整理好。如果資料來源、證據整理與引用流程不穩定，即使接上更好的模型，也只會生成更流暢但不一定更可靠的內容。

## 修改重點

這一天我對專案做出一個重要修正：

修改前：

```text
核心是 AI 生成品質
```

修改後：

```text
核心是資料搜尋品質與證據整理品質
```

也就是說，ResearchForge 的核心不是「模型有多強」，而是「資料是否被正確找到、整理、引用」。

我也開始把模型整合往後排。未來當然可以接 OpenAI API、本地 Ollama、Gemma 或其他模型，但現在最應該先完成的是資料前處理與研究流程。

## 遇到的困難

這一天主要遇到的是架構性困難，而不是單一程式錯誤。

第一個困難是，我發現「主題理解」本身就是一個大問題。如果使用者輸入「都市熱島效應對校園環境與學生學習舒適度之影響」，系統需要知道這是環境科學、教育環境與學生舒適度的研究，而不是單純作文或政策評論。

第二個困難是，搜尋來源不只是把題目丟進搜尋引擎。好的搜尋需要拆關鍵詞、擴展同義詞、判斷領域、排除不相關資料，甚至要知道哪些資料適合高中研究報告使用。

第三個困難是，我開始感受到 token、額度與時間成本。每一次讓 AI Agent 修改或思考，都可能消耗預算。如果提示詞不精準，就會浪費大量資源。

## 解決方式

我選擇先建立「小漏斗」概念，也就是讓每一階段只做一件清楚的事：

- 主題理解只負責判斷研究領域與變項。
- 關鍵詞生成只負責產生搜尋查詢。
- 來源搜尋只負責找資料。
- 來源管理只負責讓使用者接受或拒絕。
- 證據卡只負責整理可引用重點。
- 報告生成只負責根據證據寫內容。

這樣做的好處是，如果結果不好，可以知道是哪一段出了問題，而不是整個系統一起混亂。

## 是否想過放棄

這一天沒有完全想放棄，但開始感覺專案難度比原本高非常多。原本只是想做報告生成器，現在卻變成要設計一套研究資料處理流程。

不過我也發現，正因為它困難，才比較有學習價值。如果只是呼叫 AI API 生成文章，作品深度會不夠；但如果能把資料搜尋、證據整理與報告生成串起來，就更能展現我的思考與實作能力。

## 當日反思

這一天我學到，AI 專案不能只看最後輸出文字，而要看中間資料如何流動。真正的系統價值往往藏在看不到的中間流程裡，例如資料清理、來源排序、證據抽取和錯誤控制。

## 次日規劃

下一步要開始讓不同模組之間有更清楚的責任分配，尤其是 Research Writing Orchestrator 與 Plugin Contract。這樣才能避免每個功能互相混在一起。

# 2026/06/13｜建立 Orchestrator 與 Plugin Contract：讓系統從單一生成變成模組化流程

## 當日目標

這一天的目標是把 ResearchForge 從單純的報告生成器，轉向更完整的研究寫作流程系統。我開始處理兩個重要概念：

1. Research Writing Orchestrator
2. Plugin Contract

前者負責安排整個研究寫作流程，後者負責規範不同模組之間的輸入與輸出。

## 實作內容

### 1. Research Writing Orchestrator

我開始建立研究寫作流程協調器。它的作用不是直接寫報告，而是負責安排任務順序。例如：

```text
取得主題
→ 判斷研究方向
→ 要求搜尋來源
→ 收集來源資料
→ 整理證據
→ 建立章節架構
→ 生成各章節內容
→ 組合完整報告
```

這個設計讓我理解，AI 報告生成不應該只有一個巨大 prompt，而是應該拆成多個有職責的步驟。這樣才容易維護，也比較容易驗收。

### 2. Plugin Contract

我也開始處理模組合約。也就是規定每個模組應該輸入什麼、輸出什麼。例如來源搜尋模組不能只回傳一段文字，而應該回傳結構化資料：

```text
title
url
authors
year
abstract
sourceType
relevanceScore
```

證據整理模組也應該輸出固定格式，例如：

```text
evidenceSummary
keyFinding
method
limitation
usableQuoteOrParaphrase
relatedSection
```

這樣後面的報告生成模組才能穩定使用前面的資料。

### 3. DOCX 輸出測試

這一天也確認 DOCX 功能可以正常運作。這對 ResearchForge 很重要，因為學生或使用者最後通常不是只需要網頁文字，而是需要可下載、可編輯、可提交的文件。

DOCX 功能成功後，我更確認這個專案不是只有展示頁面，而是有實際輸出價值。

## 修改重點

這一天的最大修改，是讓系統架構從「一個大功能」變成「多個小模組」。

修改前：

```text
generateReport(topic)
```

修改後：

```text
understandTopic(topic)
searchSources(query)
extractEvidence(sources)
buildOutline(evidence)
generateSections(outline, evidence)
exportDocx(report)
```

這種拆法讓專案變得更像真正的軟體工程，而不是單純的 AI 輸出工具。

## 遇到的困難

第一個困難是模組化會讓系統變複雜。原本只要讓 AI 生成文章，現在卻要處理多個模組的資料傳遞。每個模組都可能出錯，而且格式一旦不一致，後面就無法接上。

第二個困難是，我需要理解很多自己原本不熟的概念，例如 API contract、資料格式、文件輸出、前後端資料流。這些不是單純寫一個頁面就能解決的。

第三個困難是額度與任務接續問題。AI Agent 有時會因為額度不足中斷，因此我必須想辦法讓任務可以被保存、接續與驗收。

## 解決方式

我開始要求每個功能都要有明確驗收標準。例如：

- DOCX 是否真的可以下載？
- 下載後是否能開啟？
- Plugin Contract 是否有明確欄位？
- Orchestrator 是否只是概念，還是真的能串接流程？

# 2026/06/14｜來源管理與 UI 流程：讓使用者能參與資料篩選

## 當日目標

這一天的目標是改善來源管理與使用者介面流程。因為 ResearchForge 的核心不是讓 AI 自動決定一切，而是讓使用者能夠檢查、接受或取消資料來源。

我當時思考的問題是：

1. 一次應該顯示多少資料來源？
2. 使用者接受來源後，畫面是否應該自動收合？
3. 來源卡與證據卡是否都要顯示在前端？
4. 如果來源太多，學生是否會懶得檢查？
5. 如果來源太少，報告是否缺乏證據？

## 實作與規劃內容

我開始設計來源管理的互動流程：

```text
系統搜尋資料
→ 顯示來源卡
→ 使用者檢查摘要
→ 點選接受來源
→ 來源自動摺疊
→ 使用者可取消接受
→ 已接受來源進入報告生成流程
```

這個設計有兩個目的。

第一，讓使用者能主動參與資料篩選。研究報告不應該完全由 AI 決定來源，使用者應該能看到並判斷來源是否可信。

第二，避免畫面太長。如果每筆來源都展開顯示，使用者會很快失去耐心。接受後自動摺疊，可以讓下面的資料往上移，提升操作效率。

## 修改重點

這一天我對前端顯示做出重要修正：

1. 來源卡可以顯示在前端，因為使用者需要檢查來源。
2. 證據卡不一定要完整顯示在前端，因為它比較像後端中間資料。
3. 接受來源後應自動摺疊，避免畫面太長。
4. 使用者必須能取消接受，避免誤選。
5. 來源數量應有基本下限，至少要有足夠資料支撐報告。

我也開始認為，最基本應該提供約 10 筆資料。太少會讓報告沒有足夠依據，太多則會造成使用者負擔。因此來源數量需要取得平衡。

## 遇到的困難

第一個困難是 UI 與資料流程互相影響。來源管理看似只是前端卡片，但其實會影響後端報告生成。如果使用者接受或取消來源，後端必須知道哪些來源可以用、哪些不能用。

第二個困難是畫面區塊太擠。來源、證據卡、報告輸出如果都放在右側，頁面會被拉得很長，使用者很難掌握目前進度。

第三個困難是我需要判斷哪些資料應該讓使用者看到，哪些資料應該留在系統內部。這不只是工程問題，也是產品設計問題。

## 解決方式

我把資料分成兩種層級：

前端顯示層：

- 來源標題
- 作者或出版資訊
- 摘要
- 連結
- 接受／取消按鈕
- 摺疊狀態

後端處理層：

- 證據片段
- 可引用重點
- 方法與限制
- 對應章節
- 來源權重
- 報告生成依據

這樣既能保留完整資料，又不會讓使用者介面過度複雜。

## 是否想過放棄

這一天的挫折主要來自 UI 反覆修改。有些功能看起來很小，例如「接受後摺疊」，但實際上涉及狀態管理、畫面更新與資料傳遞。當修改後刷新頁面卻沒有明顯變化時，會讓人懷疑是不是做錯了，或是 AI Agent 沒有真的改到關鍵地方。

不過我沒有放棄，而是改用人工驗收的方式，一個功能一個功能檢查。

## 當日反思

這一天我學到，使用者介面不只是美觀，而是研究流程的一部分。來源卡的設計會影響使用者是否願意檢查資料，也會影響報告生成是否可信。

我也理解到，產品設計中很重要的一點是：不是所有後端資料都應該顯示給使用者。好的系統應該在內部處理複雜性，在前端呈現清楚的決策點。

## 次日規劃

下一步要處理品牌定位與專案差異化。我需要更清楚定義 ResearchForge 與一般 ChatGPT、一般報告生成器之間的差別。

# 2026/06/15｜品牌與定位：ResearchForge 不應該只是另一個 ChatGPT 包裝

## 當日目標

這一天的重點是重新確認 ResearchForge 的品牌定位與核心價值。我開始思考，如果使用者已經可以直接用 ChatGPT 寫報告，那 ResearchForge 必須提供什麼不同的價值？

這一天也開始討論 Forge 風格的品牌設計，例如鍛造室、金屬、火光、紙張、報告與文獻的結合。雖然 UI 很重要，但我也必須避免過早投入過多時間在外觀上，而忽略核心功能。

## 實作與規劃內容

我開始把專案名稱與風格往 ResearchForge 收斂。

「Forge」代表鍛造，不只是生成文字，而是把零散資料、文獻、證據與想法鍛造成一份完整報告。這個意象很符合專案方向：

```text
原始資料 = 礦石

證據卡 = 鍛造中的零件
報告架構 = 模具
```

這個比喻讓我更清楚 ResearchForge 的產品精神：它不是直接變出一篇文章，而是將資料加工、整理、驗證後，逐步鍛造成研究報告。

## 修改重點

這一天我進一步確認，ResearchForge 不應該把讀書心得、簡報大綱、一般作文等功能放在核心位置。這些功能雖然可以增加使用場景，但會讓專案失去特色。

這個修正讓專案更聚焦，也降低了短期內完成 MVP 的壓力。

第一個困難是我個人其實很喜歡 Forge 風格 UI，也想把網站做得很有特色。但如果太早投入視覺設計，可能會消耗很多時間，卻沒有改善核心功能。

第二個困難是功能取捨。很多功能看起來都值得做，但目前不一定該做。對學生專案來說，最難的不是想功能，而是決定哪些功能暫時不做。

第三個困難是我開始擔心，前面 Codex 做的努力是否會因為方向修正而白費。當我決定縮小範圍時，會擔心之前做的泛用報告功能是否變得沒用。

## 解決方式

我重新定義「白費」這件事。前面做過的功能並不是浪費，因為它們幫助我發現哪些方向不適合、哪些功能會讓產品失焦。這些試錯本身就是專案學習的一部分。

我也把 UI 設計改成未來階段，而不是當前主線。當前主線仍然是：

```text

→ 來源管理
→ 證據整理
→ 報告生成

```

## 是否想過放棄

這一天有一種「方向焦慮」。因為我發現如果 ResearchForge 要做出差異，就不能只靠 AI 生成文字，而必須做更難的資料整理與引用流程。這讓專案難度上升，也讓我短暫懷疑自己是否能完成。

但同時，我也因為找到更清楚的定位而重新有動力。因為 ResearchForge 如果能專注文獻與證據，就真的能和一般 AI 工具有區別。

## 當日反思

這一天我學到，好的專案定位需要經過刪減。不是把所有功能都留下，而是要找出最能代表作品價值的部分。對 ResearchForge 來說，最有價值的不是「AI 寫得快」，而是「資料整理得可靠」。

# 2026/06/16｜模型整合與方向反思：先做好資料流，再追求 AI 效果

## 當日目標

這一天我主要思考 AI 模型在 ResearchForge 中的角色。因為目前即使還沒有完整接入強 AI，前面的資料整理流程已經開始展現效果。我開始思考：如果後面接入本地 AI 或雲端模型，是否能讓效果更突破？

同時，我也重新確認：即使接上模型，也不能改變專案初衷。ResearchForge 的核心仍然是來源搜尋與專業化報告，而不是變成萬用 AI 寫作站。

## 實作與思考內容

我開始比較兩種方向：

### 方向一：直接強化模型

優點：

- 可能快速提升文字品質
- 能讓摘要與報告更流暢
- 使用者感受可能更明顯

缺點：

- 成本可能上升
- 如果來源資料不好，模型再強也會生成不可靠內容
- 容易讓專案變回「靠 AI 寫文章」

### 方向二：先強化資料流程

優點：

- 能提高報告可信度
- 能和一般 ChatGPT 做出差異
- 未來接任何模型都能受益
- 比較符合研究工具定位

缺點：

- 前期開發較繁瑣
- 使用者可能一開始看不出背後價值
- 需要更多測試與資料結構設計

經過比較後，我決定目前應該優先走第二個方向，也就是先強化資料流程。

## 修改重點

這一天我把 AI 模型整合的優先順序往後移。不是不接模型，而是等來源搜尋、證據整理與報告生成流程更穩定後，再接模型才有意義。

新的規劃是：

```text
先完成資料搜尋與來源管理
→ 再完成證據卡與報告架構
→ 再接 AI 模型優化摘要與文字
→ 最後處理 UI、帳號與後台
```

這樣可以避免把模型當成萬能解法。

## 遇到的困難

第一個困難是模型選擇很容易讓人分心。我會思考本地模型、雲端模型、Gemma、Ollama、OpenAI API 等方案，但這些其實都不是當前最核心的問題。

第二個困難是成本與效能。若大量使用雲端模型，成本會變高；若使用本地模型，設備效能、模型能力與部署方式又會變成新問題。

第三個困難是，我必須抵抗「先接模型看起來比較厲害」的誘惑。因為對展示來說，AI 效果很吸引人，但對系統品質來說，資料流才是根本。

## 解決方式

我把模型定位成「後段增強器」，而不是「系統核心」。也就是說，模型負責幫忙摘要、改寫、生成章節，但它必須基於前面整理好的來源與證據。

我也重新確認目前不處理：

- 帳號系統
- 後台管理
- 完整商業化功能
- 過度 UI 美化
- 太多報告類型

這些都等主功能完成後再說。

## 是否想過放棄

這一天比較不是想放棄，而是擔心路線選錯。如果先做資料流，短期展示效果可能沒有直接接 AI 模型那麼驚人；但如果先接模型，長期可能會失去專案差異。

最後我選擇相信原本的核心：整理文獻並提供有價值的內容。這也是 ResearchForge 名字中 Forge 的意義——把資料鍛造成報告，而不是讓 AI 憑空生成。

## 當日反思

這一天我學到，技術選型不能只看哪個模型最強，而要看哪個選擇最符合產品核心。對 ResearchForge 來說，模型只是工具，資料流程才是主體。

下一步要整理這段時間的開發紀錄，將專案從零散開發過程轉化為可以展示給教授或審查者看的學習歷程材料。

第一，專案從「讓 AI 寫報告」轉變成「讓系統搜尋、整理、引用資料後再生成報告」。這讓 ResearchForge 和一般 ChatGPT 產生差異。

第二，專案從「功能越多越好」轉變成「核心流程先穩定」。我暫時延後帳號、後台、UI 美化與泛用報告類型，先專注來源搜尋、證據整理與文件輸出。

第三，專案從「一次生成」轉變成「模組化研究流程」。透過 Orchestrator、Plugin Contract、來源管理與證據卡概念，整個系統開始具備更清楚的工程架構。

這段過程中，我遇到許多困難，包括專案範圍過大、主題理解不準、搜尋結果不穩、UI 過度複雜、AI Agent 額度限制、版本管理壓力與模型選擇焦慮。但我沒有因為這些問題停止，而是透過縮小範圍、拆解流程、人工驗收與重新排序優先順序，逐步修正專案。

對我來說，ResearchForge 不只是一個網站作品，也是一段完整的自主學習紀錄。它記錄了我如何從問題出發，進行資料研究、技術實作、錯誤修正、產品定位與長期規劃。未來如果繼續完成來源搜尋、證據整理、引用生成與 DOCX 輸出，它將能成為一個真正有實用價值的研究輔助工具。

## 四、目前規劃修正後的開發路線

### 第一階段：穩定來源搜尋

目標是讓系統能根據不同研究主題找到至少 10 筆相關資料，並避免搜尋結果偏離主題。

### 第二階段：完成來源管理

讓使用者能接受、取消、摺疊與重新檢查來源，並將已接受來源送入報告生成流程。

### 第三階段：建立證據卡

從來源中整理出摘要、研究方法、重要發現、限制與可引用重點，作為後續生成依據。

### 第四階段：整合報告生成

讓報告內容根據已接受來源與證據卡生成，而不是只根據主題直接生成。

### 第五階段：完善 DOCX／PDF 輸出

讓使用者可以下載章節清楚、格式穩定、含來源清單的正式文件。

### 第六階段：進行 UI 與品牌優化

等核心功能穩定後，再加入 Forge 風格的品牌圖標、配色、視覺設計與更完整的使用者體驗。

## 五、這段專案對我的學習意義

ResearchForge 讓我學到的不只是寫程式，而是如何面對一個真實專案從模糊到清楚的過程。

我學到：

1. 做 AI 專案不能只依賴模型，還要重視資料來源與流程設計。
2. 做網站不能只看 UI，還要理解前後端資料如何流動。
3. 做產品不能功能越多越好，而是要有明確定位。
4. 遇到困難時，不一定代表要放棄，也可能代表原本規劃需要修正。
5. 學習歷程最重要的不是包裝成功，而是呈現真實的思考、嘗試與改進。

這也是我希望教授能看到的部分：ResearchForge 不是一天做出的作品，而是我每天持續研究、實作、卡關、修正與重新規劃後慢慢鍛造出來的成果。
